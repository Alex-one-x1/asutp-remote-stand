## Что было сделано:

### Занятие 1 — чистая установка контроллера, 11.09.2026

- записал Raspberry Pi OS Lite Bookworm 64-bit на карту через Imager;
- в преднастройке задал: имя хоста, пользователя, часовой пояс, раскладку, SSH по ключу, Wi-Fi;
- нашёл на VM ключ с чужим комментарием, проверил его, сгенерировал новый своей парой;
- подключил Raspberry Pi3b кабелем к роутеру; Wi-Fi тоже поднялся, оба интерфейса получили адреса по DHCP;
- зашёл с рабочей VM Ubuntu 24.04 по SSH без пароля.

### Занятие 2 — сети: адресация, маршруты, 11.09.2026

- перевёл eth0 RPi3b на статику через nmcli: адрес 192.168.1.111/24, шлюз, DNS, метод manual;
- проверил, что статика пережила перезагрузку и маршрут стал proto static;
- отключил кабель Ethernet при "живом" Wi-Fi, посмотрел, как снимаются маршруты, подключил обратно, записи и подключение восстановилось;
- на VM нашёл конфликт двух конфигов netplan: свой 01-netcfg.yaml перекрывался 50-cloud-init.yaml с dhcp4: true;
- отключил cloud-init от управления сетью, удалил его конфиг, заменил устаревший gateway4 на routes, закрыл права на файл;
- проверил через netplan try с откатом по таймауту, применил, убедился в работоспособности после перезагрузки.

### Занятие 3 — доступ и обновление, 12.09.2026

- выяснил, что для моего пользователя настроен беспарольный sudo; оставил осознанно, понимая цену;
- разобрал разницу между обновлением списка пакетов и обновлением установленных (и право full-upgrade удалять пакеты);
- обновил систему, ядро перешло с 6.12.93 на 6.12.96;
- проверил, что парольный вход закрыт — поведением, а не чтением конфига: запросил вход с запретом ключа и получил Permission denied (publickey);
- посмотрел через ss слушающие сокеты: наружу открыт только 22;
- включил персистентный журнал параметром Storage=persistent и задал лимит размера; каталог /var/log/journal уже существовал, работу сделал параметр;
- убедился, что журнал переживает перезагрузку: в journalctl --list-boots появилась предыдущая загрузка.

### Занятие 4 — сервисы (systemd), 17.09.2026

- разобрал модель: systemd управляет юнитами, сервис — один из типов юнита, описывается текстовым файлом (что запускать, от чьего имени, что делать при завершении);
- создал свой юнит /etc/systemd/system/asutp.service: User, абсолютные пути в ExecStart, Restart=always, RestartSec=5;
- в качестве тела сервиса взял Python-скрипт, написанный ИИ по моему запросу;
- проверил Restart=always через kill -9: PID сменился, процесс поднялся сам через 5 секунд;
- разделил start (запуск сейчас) и enable (автозапуск, ссылка в multi-user.target.wants); в статусе это независимые слова active и enabled;
- убедился перезагрузкой, что сервис поднимается сам без единой команды;
- прочитал журнал сервиса через journalctl -u с ключами -b, -f, -n.

### Занятие  — права доступа, 20.09.2026

- разобрал модель прав rwx, владельца и группу, отличие смысла битов для каталогов;
- воспроизвёл отказ доступа: файл 644 недоступен чужому пользователю из-за прав 700 на каталоге выше по пути;
- посмотрел свои группы через id, нашёл среди них dialout, gpio, adm и понял, что из них где понадобится;
- осмотрел узел: ps aux, top, df -h, free -h; запас на карте 11 ГБ, доступной памяти 760 МБ.
